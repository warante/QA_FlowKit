# EPIC-P5 - Distribution, extensibility and ecosystem

Goal: package the product for discovery and growth: an official Claude Code plugin (while keeping
the npm CLI as the multi-agent source of truth and full adapter parity), declarative extensibility
for custom validators and specialists, local value metrics computed from the event log, and the
parser debt that blocks richer Gherkin/YAML features.

Exit gate: a Claude Code user can install QA FlowKit as a plugin from a marketplace and get
namespaced skills, hooks and the orchestrator agent; a team can add its own validator without
forking; `qa-flowkit metrics` reports workflow KPIs from any target repo; Gherkin and YAML parsing
handle the full feature set introduced by P3/P4.

## P5-US-01 - Claude Code plugin

As a Claude Code user, I want to install QA FlowKit as a plugin so that skills, hooks and agents
arrive versioned and namespaced without running init first - and update like any other plugin.

### P5-T-001 - Package the Claude adapter as an official Claude Code plugin

Status: Done
Priority: P2
Depends on: P1-T-001, P1-T-002 (hooks), P1-T-004 (modern skills)

Description: build a plugin from the existing adapter content with a single-source generation
step (no hand-maintained duplicates), validated in CI.

Implementation notes:

- Create `plugin/` (source-repo folder, excluded from npm pack) generated by a new script
  `.github/scripts/build-claude-plugin.mjs` from `.qa-ai/adapters/claude/` content:
  - `plugin/.claude-plugin/plugin.json`: name `qa-flowkit`, description (bilingual one-liner),
    version read from `package.json`, author, homepage.
  - `plugin/skills/` from the adapter commands (skills become `/qa-flowkit:qa-init` etc.).
  - `plugin/agents/` from the adapter agent.
  - `plugin/hooks/hooks.json` from the P1 hook fragment (paths adjusted to invoke the target
    repo's `.qa-ai/scripts/hooks/*` when present, with a clear error message instructing
    `npx qa-flowkit init` when `.qa-ai/` is absent).
  - Skills that operate on a repo without `.qa-ai/` must degrade to instructing
    `npx qa-flowkit init` (the plugin complements, never replaces, the installed framework).
- Marketplace: add `.claude-plugin/marketplace.json` at the repo root listing the plugin, so the
  GitHub repo itself is installable as a marketplace
  (`claude marketplace add warante/QA_FlowKit`). Submission to the community marketplace is a
  manual maintainer step - document it in the release checklist, do not automate.
- CI: new job runs the build script and `claude plugin validate plugin/` (guard with
  `command -v claude` and skip-with-notice when the CLI is unavailable in CI; in that case run the
  build script's own structural checks: manifest schema, file presence, JSON parseability).
- Generation is deterministic: running the build twice produces identical output; the build fails
  if `plugin/` has uncommitted drift from the adapter sources (parity enforcement).
- Add a post-init hint: when `init` detects `.claude/` and the plugin is not installed, print one
  line suggesting the plugin install command (no network calls).

Acceptance criteria:

- [x] `node .github/scripts/build-claude-plugin.mjs` generates `plugin/` with a valid manifest,
      all current Claude adapter skills, the agent and hooks; running it twice yields no diff
      (`git diff --exit-code plugin/` passes after second run).
- [x] CI job validates the plugin (or runs structural fallback checks) and fails when a skill is
      removed from the adapter without rebuilding (drift test verified once during development).
- [x] `plugin/` and the marketplace manifest are excluded from the npm pack
      (`verify-npm-pack.mjs` asserts it).
- [x] Plugin skills keep bilingual descriptions; `qa-gate` skill keeps
      `disable-model-invocation: true`.
- [x] New doc `docs/qa-ai/claude-plugin.md`: install via marketplace, relationship between plugin
      and `npx qa-flowkit init` (plugin = host surface; framework = repo substrate), update story;

## P5-US-02 - Declarative extensibility

As a platform team, I want to register custom validators and specialists in configuration -
without forking the framework - so that our org-specific rules run inside the same harness and
gates.

### P5-T-002 - Support config-declared custom validators in the harness allowlist

Status: Done
Priority: P2
Depends on: P0-T-005 (config schema)

Description: replace the hardcoded-only validator allowlist with hardcoded built-ins plus
config-declared repo-local validators, with strict safety constraints.

Implementation notes:

- Config (schema + docs):

  ```yaml
  validators:
    custom:
      - id: org-naming-rules
        script: qa-custom/validate-naming.mjs # repo-relative, path-safe
        phases: [gherkin] # contract phase ids where it runs
        blocking: true # false = warnings only
  ```

- Constraints enforced at load time: `id` matches `^[a-z][a-z0-9-]{2,40}$` and must not collide
  with built-in ids; `script` resolves inside the repo (resolveRepoPath) and must exist; `phases`
  values must exist in the workflow contract; scripts are executed with `process.execPath`
  (Node only, never shell), cwd = repo root, no extra env, and the documented validator contract:
  exit 0 pass / non-zero fail, findings on stdout, `--json` support required.
- Execution: `harness-validation.mjs` runs custom validators after built-ins for their declared
  phases; `validate-target.mjs` includes them; failures of `blocking: false` validators are
  recorded as warnings in events, never block.
- Security note in docs and `SECURITY.md`: custom validators are repo code, reviewed like any
  other code; the framework adds path-safety but does not sandbox them (same trust level as npm
  scripts).
- `doctor` verifies each declared validator: file exists, responds to `--json` with parseable
  output on a `--self-test` invocation (define `--self-test` in the contract: exit 0, no side
  effects).
- Template example `qa-custom/validate-naming.example.mjs` generated with
  `init --with-doc-templates`.

Acceptance criteria:

- [x] A fixture custom validator declared for the `gherkin` phase runs during `run check` and its
      failure blocks the phase when `blocking: true`; with `blocking: false` the phase completes
      and a warning event is recorded (both tested).
- [x] Each constraint violation fails config/doctor validation with a specific message: bad id,
      id collision with a built-in, missing script, path escape, unknown phase id.
- [x] `validate-target --json` output includes custom validator results.
- [x] The validator contract (`exit codes, stdout, --json, --self-test`) is documented in
      `docs/qa-ai/extensibility.md`; example file ships and passes its own self-test.
- [x] `SECURITY.md` documents the trust model for custom validators.
- [x] Global Definition of Done passes.

## P5-US-03 - Local workflow metrics

As a QA manager, I want workflow KPIs computed locally from the run event log so that I can show
before/after value (cycle time, validation failure rates, rework) without sending telemetry
anywhere.

### P5-T-003 - Implement qa-flowkit metrics from the run event log

Status: Done
Priority: P3
Depends on: none

Description: add a `metrics` command aggregating all runs under `.qa-ai/state/runs/` into KPIs,
human-readable and `--json`.

Implementation notes:

- `.qa-ai/scripts/qa-metrics.mjs` + `bin/qa-flowkit.mjs` `commandMap` entry `metrics`. Flags:
  `--json`, `--since <ISO date>`, `--run <run-id>`.
- KPIs computed exclusively from `events.jsonl` + `run.json` files (read-only, lock-respecting):
  runs started/completed/blocked; per-phase: median and p90 duration (first activation to
  completion), validation failure rate (failed checks / total checks), retry count; approval
  wait time (approval-blocked to approval-recorded); rework signal (modification approvals per
  run); totals per track. Durations derive from event timestamps; runs without terminal events
  count as in-progress.
- Output: human table (English, like all CLI output) and a stable JSON schema documented in the
  CLI reference. No network, no writes (pure read command - assert no state mutation in tests).
- Privacy statement in docs: metrics never leave the repository; no artifact contents are read.

Acceptance criteria:

- [x] Against a fixture state directory with three runs (one completed, one blocked, one
      in-progress), `metrics --json` reports the documented fields with correct counts and
      durations (deterministic fixture timestamps).
- [x] `--since` filters by run start; `--run` scopes to one run; empty state prints a friendly
      zero-runs message and exits 0.
- [x] The command performs no writes under `.qa-ai/state/` (test asserts directory mtime/content
      hash unchanged).
- [x] Malformed event lines are skipped with a stderr warning, never a crash (corrupt fixture
      test).
- [x] `metrics` in CLI help, `docs/qa-ai/cli-reference.md`, and a usage section in
      `docs/qa-ai/pilot-methodology.md` (replacing manual measurement steps where applicable);
      README EN/ES mention local metrics.
- [x] Global Definition of Done passes.

## P5-US-04 - Parser debt

As a maintainer, I want full-fidelity Gherkin and strictly-validated YAML parsing so that the
syntax introduced by P3/P4 rests on a parser, not regex patches.

### P5-T-004 - Replace line-regex Gherkin parsing with a structured parser

Status: Done
Priority: P2
Depends on: P3-T-002, P4-T-003 (their syntaxes define the parser's required coverage)

Description: implement a proper dependency-free Gherkin parser (tokenizer + AST) under
`.qa-ai/scripts/lib/gherkin-parser.mjs` and migrate `gherkin-validate.mjs` and every feature-
reading module to it, preserving all existing validation messages.

Implementation notes:

- Parser scope: Feature/Rule/Background/Scenario/Scenario Outline + Examples, steps, docstrings,
  data tables, tags, comments, `# language:` directives for `en` and `es` keyword sets (reuse
  official Gherkin keyword translations for the two supported languages), line/column positions
  on every node.
- Migration: `gherkin-validate.mjs`, traceability feature reading, coverage checking, exporters
  (P3-T-006) and statistical-step validation (P4-T-003) consume the AST. Validation findings keep
  their existing message text and line numbers (regression: the entire current validator test
  suite and the P3-T-003 dataset pass without expectation changes, except where the old parser
  was provably wrong - each such change documented in the PR).
- Edge cases that must now parse correctly (add tests): multi-line scenario descriptions,
  docstrings containing `Scenario:`-like text, data tables with escaped pipes, comments between
  tags and scenario, CRLF files, BOM.
- Performance budget: parsing 500 fixture features completes under 5 seconds on CI (benchmark
  test with generated fixtures).

Acceptance criteria:

- [x] `gherkin-parser.mjs` exists with exported `parse(text)` returning a documented AST; unit
      tests cover every node type and both keyword languages.
- [x] All existing validator tests pass unmodified (or with documented corrections); the
      gherkin-quality dataset still validates.
- [x] The six edge cases parse correctly (dedicated tests); the old regex path is deleted (no
      dual implementation).
- [x] Benchmark test passes within budget.
- [x] `docs/qa-ai/architecture.md` updates the parsing section.
- [x] Global Definition of Done passes.

### P5-T-005 - Strict YAML loading for config and release gate files

Status: Done
Priority: P3
Depends on: P0-T-005

Description: extend the native YAML reader to cover the constructs the config schema actually
needs (nested maps, sequences of maps, quoted strings, multi-line strings) with strict, located
errors, and route all YAML reads through it.

Implementation notes:

- Extend `.qa-ai/scripts/lib/utils.mjs` (or split into `yaml.mjs`): supported subset = maps,
  sequences (including sequences of maps for `validators.custom` from P5-T-002 and
  `execution.resultsPaths`), scalars with single/double quotes and escapes, `|` and `>` block
  strings, comments; explicitly unsupported (anchors, aliases, tags, flow style beyond simple
  inline lists) produce an error naming the line and the unsupported construct - never silent
  misparsing.
- All YAML consumers (config load, presets, release-gate validator, profile import/export) use the
  one loader; loader errors include file, line and column.
- Fuzz-ish test: every preset, every fixture config and every fixture release gate round-trips
  (load -> re-serialize via the existing writer -> load) to a deep-equal structure.

Acceptance criteria:

- [x] The new constructs parse (table-driven unit tests, including the P5-T-002 `validators.custom`
      shape); each unsupported construct yields a located error (tests for anchor, alias, tag,
      nested flow mapping).
- [x] Round-trip test passes for all presets and fixtures.
- [x] No file under `.qa-ai/scripts/` parses YAML by any other path (grep-based test or lint rule
      asserting single import point).
- [x] `docs/qa-ai/config-schema.md` documents the supported YAML subset.
- [x] Global Definition of Done passes.
